# TG Server Control

[Project page](https://skazimax.github.io/tg-server-control/) ·
[Privacy policy](https://skazimax.github.io/tg-server-control/privacy.html) ·
[Terms of service](https://skazimax.github.io/tg-server-control/terms.html)

Отдельный Telegram-бот для статусов и управления сервисами домашнего сервера.
Он не является частью `egg_cam`: мониторинг яиц — лишь один из подключённых
status-провайдеров.

Кнопка «Румянцево» открывает отдельный экран показателей дома.
Температура и влажность на обоих этажах берутся из таблицы YDB
`nest_environment_readings`, куда их каждые пять минут записывает
отдельный облачный сборщик. Запись старше 15 минут считается
неактуальной. Для температуры на улице и в колодце пока выводятся
заглушки.
Уровень воды берётся из последнего свежего измерения YDB; при
его отсутствии выводится предупреждение «нет данных». Остальные показатели
будут подключаться к реальным источникам независимо друг от друга.

## Расширение статуса

Общий `/status` запускает по имени все исполняемые файлы из
`/etc/tg-server-control/status.d`. Каждый provider печатает одну короткую строку:

```text
⏹ Яйца
✅ VPN: AdGuard
✅ MTProto
✅ Румянцево(SSTP)
❌ Колодец
```

Чтобы добавить показатель, положите исполняемый файл `NN-name` в `status.d`.
Префикс `NN` задаёт порядок. Provider должен самостоятельно обработать ошибку и
напечатать строку с подходящим значком. Шаблон находится в
`status-provider.example`.

## Конфигурация

- `/etc/tg-server-control/bot.env` — Telegram token, список администраторов и
  путь к offset; файл не хранится в Git;
- `/etc/tg-server-control/well.env` — настройки проверки данных колодца;
- `/etc/tg-server-control/status.d` — установленные status-провайдеры;
- `/var/lib/tg-server-control/update_offset` — последний обработанный update.
- `/etc/tg-server-control/ydb-sa-key.json` — отдельная копия ключа чтения YDB,
  `0600 root:root`; не хранится в Git.

Бот работает как системный пользователь `tg-server-control` без shell и общих
прав sudo. Код находится в `/opt/tg-server-control/app`, Python-окружение —
в `/opt/tg-server-control/venv`; оба принадлежат root и недоступны боту для записи.
Sudo разрешает только перечисленные одноаргументные команды helper. Провайдеры
запускаются root через защищённое Python-окружение в изолированном режиме `-I`.
Домашние каталоги скрыты от службы. Для helper оставлена запись в root-owned
`/etc/sing-box`; пользователь бота сам записывать туда не может.

Исходящий Telegram-трафик использует общий SOCKS
`socks5h://127.0.0.1:1079`, предоставляемый `tg-vpn-failover`.

### Сетевые команды

Экран «Статус сети» показывает текущий upstream VPN, MTProto, таймер
failover, SSTP и маршрут до камеры. Кнопка «Переключить VPN» вручную
меняет активный upstream `AdGuard → SKIPP(VLESS)` или
`SKIPP(VLESS) → AdGuard`. Перед применением `tg-vpn-failover` проверяет новый
маршрут до Telegram и отменяет переключение, если он недоступен.

Меню slash-команд Telegram синхронизируется из кода при запуске бота.

## Установка

```bash
sudo ./install.sh
sudo systemctl enable --now tg-server-control.service
```

Перед первым запуском нужно создать `bot.env` и `ydb-sa-key.json` с правами
`0600 root:root` в `/etc/tg-server-control`. Установщик намеренно не создаёт
секреты и сохраняет существующий `well.env`.

При миграции пользователя сначала остановите бота, сохраните актуальный offset,
затем выполните установщик и запустите службу. Не возвращайте старый offset из
архива: это может повторить уже обработанные команды. Установщик переносит
владение текущим offset новому пользователю и копирует ключ YDB из прежнего пути
в закрытый каталог; исходный ключ отчётов остаётся на месте.

Если `/opt/tg-server-control/venv` уже подготовлено с проверенными зависимостями,
можно выполнить `sudo env TG_CONTROL_SKIP_DEPS=1 ./install.sh`. Импорт необходимых
модулей проверяется и в этом режиме. После обычного обновления перезапустите бота.

Отдельные настройки SSH и firewall хоста описаны в [ops/README.md](ops/README.md).
Установщик бота их автоматически не меняет.

## Достоверность статусов и журнал команд

Общий заголовок статуса имеет значок ℹ️: успешное получение экрана не означает,
что все компоненты исправны. VPN использует проверки Telegram Core и Bot API
из `tg-vpn-failover`; данные старше 90 секунд, отсутствующие данные и смена
маршрута после проверки дают предупреждение. Требуется версия failover с
`lib/status.py` и командой `tg-vpn-failover-status --mtproto`.
MTProto показывает только процесс и локальный порт 443, SSTP — процесс.
Маршрут до камеры считается нужным только через `ppp20`, настроенный для SSTP
на этом сервере. Проверка маршрута не является проверкой доступности камеры.
Отчёт без сведений о запуске не отмечается как успешно выполненный.
Каждый status-provider ограничен 30 секундами (+2 секунды на завершение).

`/var/lib/tg-server-control/commands.sqlite3` — журнал SQLite, права 0600,
владелец — пользователь бота. Он хранит update_id, ID отправителя, известное имя
команды, время, результат выполнения и доставки, а также этапы вызова helper.
Токены, произвольный текст сообщения и вывод helper в журнал не записываются.
Дополнительно краткий итог попадает в systemd journal.

Запись команды сохраняется до offset и до выполнения. Уже зарегистрированный
update не запускается повторно даже при потере offset. Повреждённый offset
останавливает запуск бота вместо молчаливого сброса. Запись offset атомарна и
синхронизируется на диск. Ошибка предварительного уведомления или подтверждения
callback не отменяет принятую команду. Ошибка команды сохраняется в ответе,
даже если последующее получение статуса успешно.

Выполнение и доставка учитываются отдельно: `success` не означает, что ответ
получен пользователем, а `sent` означает только подтверждение Telegram API.
При тайм-ауте helper либо прерывании процесса результат `unknown`: действие
могло состояться. Автоматического повтора действий и ответов нет. Проверить
фактический статус перед ручным повтором особенно важно для переключателей.
При перезапуске оставшиеся `running` становятся `unknown`; события helper
сохраняются для диагностики. Гарантии exactly-once для внешних systemd-действий
нет: сбой между записью команды и её выполнением может оставить её невыполненной.

Завершённые записи старше 90 дней удаляются не чаще раза в сутки, только если
они ниже текущего offset; `unknown` сохраняются. Журнал — операционный учёт,
не защита от изменения скомпрометированным пользователем бота.
Для просмотра без изменения базы:

```bash
sudo /usr/bin/python3 - <<'PY'
import sqlite3
with sqlite3.connect('file:/var/lib/tg-server-control/commands.sqlite3?mode=ro', uri=True) as db:
    for row in db.execute('SELECT update_id, command, execution, delivery FROM commands ORDER BY received_at DESC LIMIT 20'):
        print(row)
PY
```

При восстановлении сохранять актуальные offset и commands.sqlite3. Не подменять
их старыми копиями: это может повторить ранее выполненные команды.
